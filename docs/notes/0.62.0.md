# 0.62.0 — Vociferous Vulture

Researcher-authored text is still filtered, but the forbidden-term lists are no longer in the repository. Each interface locale keeps its own generated policy in the system SQLite store. Administrators generate and edit those lists from **System → Languages**; researcher sessions only ever see hashes.

- **Storage:** `languages.content_policy_json` holds blocked and context-sensitive terms per locale. Saving a dictionary no longer wipes an existing policy. Public language payloads expose `content_policy_ready` and omit the plaintext list.
- **Generation:** built-in English and Québec French need a one-time generate after the first administrator account exists. Installing a new locale runs policy generation after dictionary translation; a failed generate leaves the dictionary in place so it can be retried from Languages.
- **Enforcement:** the API uses the union of every ready locale policy and rejects researcher text until at least one policy exists. Matching still uses NFKC, leet substitutions, and word boundaries. Contextual terms keep the scholarly/naming exemptions.
- **API:** `GET /api/i18n/content-policy` is authenticated and returns hashes only. Per-locale GET/PUT of plaintext terms is admin-only. The public languages endpoints never include `content-policy`.
- **UI:** Languages shows a policy-needed banner and per-locale generate/edit controls. The researcher client loads hashes on sign-in and filters input locally the same way.
- **Source hygiene:** `content_filter.py` has no slur lists. Tests use dummy tokens (`zzblock`, `qwvulgar`, and similar).
