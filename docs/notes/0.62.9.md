# 0.62.9 — Steady Swift

Fixes for the review workspace and Edit document metadata, from a bug report.

- **Scrolling no longer gets stuck.** Once the review workspace was in place, the mouse wheel over the queue, the record or the details never reached the page, so nothing above the workspace could be scrolled to. Scrolling now passes to the page when a pane is at its top or bottom.
- **A changed page number can be saved.** Editing a page number in Edit document metadata and saving did nothing, without a message: the number input gave the form a number and the save code tried to trim it. This was not tied to enrichment.
- **Edits are no longer wiped.** The editor re-copied every field from the build each time the build was refreshed, and a running build is refreshed every few seconds, so a draft disappeared while you typed. A field you are editing now keeps your draft. If its value changes elsewhere in the meantime, the field says so and offers the new value.
- **Saving works during a multi-pass run.** A save was refused while enrichment passes were running. It is now allowed for everything except the main-text start and end pages, which still wait for the run to stop because they decide which text becomes records.
- **Saving reopens fewer records.** Saving document metadata used to reopen every record for review, even those whose inherited values did not change. It now reopens only the records whose inherited values, citations or classification (main text, front matter, back matter) actually changed, and the warning under the form says so. It also runs under the same lock as enrichment, so a save can no longer overwrite a pass's results.

## What is not done

- The first main-text page you set under the structural anchors and the one in the document manifest are still two separate values, so they can disagree (the reported 18 versus 53). Fixing that needs a decision about what should happen to records that already exist when the start page changes.
- The main-text pages are still refused during a run. I reproduced the scrolling problem in a test build; I have not seen the save failure on a real build, and I found the number-input cause by reading the code and reproducing it in a unit test.
