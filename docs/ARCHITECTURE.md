# Architecture overview

This document describes the current `master` architecture. For user-visible behavior see [USER_GUIDE.md](USER_GUIDE.md); for scholarly rationale and implemented-versus-intended distinctions see [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md).

## Runtime processes

- **web** — Vue 3 single-page application built by Vite and served by nginx. It proxies `/api/` to the API; Storybook is an opt-in development surface.
- **api** — one FastAPI process. `api/app/main.py` is intentionally a minimal ASGI entrypoint; `application.py` constructs the app, registers middleware/exception handling, and composes domain routers from `api/app/routers/`. Shared services are constructed in `services.py`.
- **LLM providers** — Ollama or OpenAI-compatible endpoints reached through named provider profiles.
- **Chroma** — embedded `PersistentClient` by default or an HTTP Chroma server. Chroma stores derived search/vector projections and operational caches; it is not the canonical scholarly record store.
- **document-nlp (optional)** — an isolated BookNLP adapter enabled through the `document-nlp` Compose profile. It receives bounded reviewed document text, returns derived linguistic annotations, has no corpus authority, and never downloads model weights at runtime. The API falls back gracefully when it is absent.

Background corpus/job orchestration runs in the API process. There is no external durable queue service. The optional Document Intelligence worker is a replaceable analysis provider, not a job coordinator or canonical store.

### Transports

The browser talks to the API over three deliberately separate transports, all served by the same process and proxied under `/api/`:

- **REST** (`/api/...`) owns every command and mutation: uploads, review decisions, claim validation, job creation/cancellation, schema/provider/user administration, publication, backup/restore.
- **GraphQL** (`POST /api/graphql`) is a read-only, cELF-aware query façade over shared read services (`celf_queries/`). No mutations, no subscriptions. See [GRAPHQL.md](GRAPHQL.md).
- **WebSocket** (`WS /api/ws/events`) is an authenticated realtime notification plane for job, corpus-build and model-activity progress. It is never canonical state; clients resynchronize from REST/GraphQL. See [REALTIME.md](REALTIME.md).

## Sources and corpus build flow

Corpus Builder is source-media aware rather than PDF-only. Source acquisition and corpus building are deliberately separate: acquiring or registering a SourceDocument does not start a build.

The Corpus Builder presents three researcher-facing phases, **Setup → Build & review → Publish**. Build and Review are intentionally concurrent once Record topology exists: researchers may stay on the live Build monitor or begin adjudicating available Records while enrichment continues. Internally, the frontend retains four route-backed workspaces — `setup | build | review | publish` — via `?workspace=` (`features/corpus-builder/domain/workspace.ts`, `composables/useCorpusWorkspaceNavigation.ts`) so deep links and lifecycle state remain explicit. `PdfCorpusBuilder.vue` owns mutations and the feature composables and composes `CorpusSetupWorkspace`, `CorpusBuildWorkspace`, `CorpusReviewWorkspace` and `CorpusPublishWorkspace`; the workspace components own visual composition and pass Review panes through slots. UI interpretation of build state (badge, current operation, stage rail, setup issues and section states) lives in `domain/workflowPresentation.ts` and `domain/setupState.ts`; it holds no authoritative state and makes no API calls.

1. **Discover/acquire sources (optional).** Corpus Capture resolves a researcher-selected person through Wikidata, discovers Project Gutenberg/Wikisource candidates through provider adapters, reconciles work/edition identity, and records coverage. The researcher selects candidates before acquisition. Successful acquisition registers ordinary SourceDocument assets; the capture itself remains acquisition bookkeeping.
2. **Register and validate source.** Uploads, URLs, single-library imports, and Corpus Capture acquisitions converge on the same source-registration path. Enforce format-specific byte/resource limits and reject unsafe active content before expensive extraction.
3. **Extract/transcribe.** Preserve the immutable extracted source and extractor/tool/version provenance. PDF extraction may use OCR. Audio runs a staged transcription pipeline: full-file transcription requests segment and word timestamps, WhisperX forced alignment supplies word timing when the provider does not, and diarization remains an independent timed voice-cluster result. Text/document/image/library paths have their own adapters.
4. **Normalize source spans.** Build source units with medium-appropriate coordinates. Pages/printed folios are meaningful for paged documents. Audio binds diarized speakers to aligned words, records uncertainty, then coalesces consecutive same-speaker words into timed turns. The provider transcript, diarization labels, word-level speaker evidence, and later reviewed speaker identity remain separately auditable.
5. **Structure and segment.** Reviewer-confirmed structure is authoritative. Semantic boundary proposals are validated for text conservation and coherent source mapping.
6. **Enrich.** Metadata-family tasks combine deterministic facts, optional run guidance, and bounded evidence-bound reviewed precedents. Model output is a proposal until schema/provenance checks pass.
7. **Review.** Reviewer edits are revisioned and preserve field/evidence provenance. The frontend applies ordinary review edits optimistically while serializing conflicting same-record persistence and handling rejection/rebase/rollback.
8. **Publish/index.** Validated records are serialized for publication. Vector indexes are explicit derived projections that can be rebuilt from authoritative records.

Autonomous builds use the same stages, then add a policy settlement stage before
acceptance and publication. Policy selection records its actor and configuration
separately from the selected assertion; it does not turn model-derived,
deterministic, unresolved, failed, disputed, or low-confidence state into human
confirmation. Publication metadata reports `reviewed`, `autonomous`, or `hybrid`
decision mode and evaluates cELF Core/Publication conformance independently from
that mode. Legacy unreviewed publication requests remain accepted for API
compatibility, but their conformance result is computed from source, identity,
integrity, and publication blockers rather than inferred from review status.

Corpus Capture discovery/acquisition jobs run through `job_capture.py` and the shared operation ledger. `capture_store.py` persists captures, candidates, and provider snapshots in System SQLite. Those rows are not corpus content: registered sources remain canonical SourceDocument assets, and `source_capture_links` is a many-to-many provenance association so one source can be reached by multiple captures without making a capture ID part of source identity. Interrupted capture workers are marked interrupted/failed rather than silently replayed after restart.

The Sources workspace is a compact projection over canonical source assets plus capture links and build summaries. `source_registry.py` never exposes source text or blocks in its table rows; the projection can be rebuilt from source/build state.

The compatibility storage namespace still contains `.home/pdf-corpus`; that path name is historical and must not be interpreted as a PDF-only product contract.

Extracted source blocks remain authoritative JSONL. `source_block_index.py` maintains a disposable, per-asset SQLite byte-offset lookup beside that file (`*.blocks.index.sqlite3`), not a second text store. Selected reads seek and decode only requested block IDs; a cold or changed source requires one streaming indexing pass. Index versions bind file identity, size, and nanosecond filesystem timestamps. Replacement, extraction/layout/page-label edits, and missing indexes trigger rebuilding; malformed source, identity mismatch, or a source change during lookup fails visibly. Repository source writers and reads share the existing writer lock, and index rebuilding is transactional across repository instances.

## Metadata and memory authority

DerridAI has multiple kinds of “memory”; they must not be flattened into one database concept.

- **Canonical scholarly state:** reviewed records/RecordRevisions, field assertions and review decisions, exact evidence bindings, source identity.
- **Metadata exemplars:** evidence-bound reviewed precedents derived from canonical review state. Their semantic index is rebuildable. Corrections preserve rejected values as negative evidence; confirmed absence is reusable only when explicitly evidence-bound. Selection is driven entirely by the schema's retrieval policy (`enabled`, `max_items`, `min_similarity`, `include_corrections`, `include_confirmed_absence`, `max_corrections`, `match_field_ids`): positives and corrections have separate quotas, and `match_field_ids` names other fields by stable identity whose _reviewed_ values a precedent should share. Each exemplar carries a schema-agnostic `reviewed_values` snapshot of its record; a condition is compared only when both sides are reviewed (never guessed), agreeing precedents rank first, and contradicting ones are dropped. No field name is special-cased (`metadata_exemplars.py`, `metadata_exemplar_retrieval.py`, `corpus_editorial_memory.py`). Record Review reads the same selection read-only through `metadata_precedents`.
- **Incremental exemplar projection:** ordinary changes reconcile the complete exemplar set for affected Records, including removal to an empty set. Indexed canonical reads and bounded build/Record-filtered vector reads replace full-build derivation and vector-scope churn. Unchanged rows reuse their vectors; metadata-only changes refresh the projection without embedding, and a new exemplar ID can reuse a vector from the same Record's exact unchanged context under the existing collection embedding contract. Projections retain the originating assertion ID. Pending blind second opinions are excluded from shared exemplars and cross-field reviewed-value snapshots regardless of worker reviewer context; disputed, invalid and unresolved assertions are not trusted precedents. Original Records, assertions, revisions, evidence and authority are never replaced by these projections. Record-local derivation loads only the affected Records' source-block IDs through the byte-offset lookup, preserving the complete evidence-centered context within each Record. Full rebuilds and diagnosis retain full-asset reads.
- **In-flight metadata-call coalescing:** `metadata_request_coalescer.py` shares only overlapping identical provider calls within one manager, build, Record dependency fingerprint, operation, provider role/configuration/credentials, prompt, response schema, retry budget, and output budget. Each consumer still runs its assigned immutable pipeline and domain reconciliation; schema validation and assessment-consistency checks gate sharing, and consumers receive independent response copies. The pending map holds at most 64 distinct keys, with excess keys executing normally through existing provider limits. It retains no completed cache or failed-result cache; waiting is bounded and failures remain visible. Keys, credentials and response bodies never enter coalescing telemetry. Each family ledger records actual model invocations and joined-call counts separately. Explicit operations with different run IDs do not share calls.
- **Materialized metadata-family reuse:** existing per-Record family ledgers now retain an opaque `metadata-materialized-family-v1` fingerprint after domain reconciliation, binding each requested field's value, compatibility status, evidence, and current canonical assertion. A scheduled completed family without its raw response skips generation only when its exact execution dependency fingerprint and materialized-output fingerprint both match. Input/output mismatches invalidate that family and recompute through the assigned pipeline; a missing pipeline cannot certify reuse. Citation formatting alone is not an execution dependency. Legacy normalized families without dependency fingerprints retain historical resume behavior rather than being labelled validated cache hits. No response text is added to the ledger, no parallel result store is introduced, and human ownership remains checked before automatic work.

Build performance milestones are operational fields: `topology_persisted_at` is set after validated deterministic topology is durably saved, `review_available_at` at the post-preparation review-compatible boundary, and `metadata_first_settled_at` after the first newly terminal Record merge commits and before its realtime completion hint. Those first-observed values survive later completions/resume. `text_review_available_at` instead belongs to the current preparation and is cleared before preparation/resume. Fresh topology sets it only after conservation validation and deterministic cleanup are durably saved. The backend and frontend permit text-only decisions during `constructing_records` and `document_intelligence` only with this milestone and valid topology; metadata, disposition, structural changes, and model assistance retain ordinary preparation gating. Text saves preserve the running preparation lifecycle, original extraction, human authority, and revision checks. Existing-topology resume does not yet expose the earlier boundary. None of these milestones certifies publication, browser rendering, or a semantic quality outcome.

Post-topology preparation and initial enrichment queue setup merge Record deltas against their input snapshot and current canonical state. Ordinary keys preserve intervening changes and distinguish omission from explicit null; scholarly assertions change only when their field state is unchanged and not human-owned. Text/revision/source-binding mismatches discard stale preparation output rather than rebind it. Newly reviewed scopes reject late work, while an explicit annotation rerun can refresh derived annotations of already reviewed, unchanged text without altering its scholarly assertions. Conditional `update_record` checks the queue state version within the Record/queue transaction, including external repository writers; conflicts retry at most three times, then fail visibly. Retired Records cannot be resurrected, changed repeatable members preserve historical assertions, and unchanged rows are not written. Initial topology replacement remains a distinct full-store operation; automatic validation and requeue use changed-row reconciliation. Earlier metadata or structural review unlock still requires additional scheduling coordination and readiness coverage.

- **Exemplar recovery:** SQLite triggers maintain coalesced `metadata_exemplar_dirty` tokens transactionally with canonical payload changes, including external repository writers. `metadata_exemplar_state` records the derived collection epoch and build/source/alias context fingerprint; these operational tables are not scholarly Record fields or publication content. Reviewed audit bindings and their `semantic_memory_outbox` events commit together in the system database. Projection acknowledges only captured tokens/event IDs after successful vector writes, preserving newer edits and retrying partial failures. Tasks are coalesced per build and drain bounded batches. Full Record-store replacement, broad dependency invalidation, explicit repair and missing/incompatible collection recovery retain the full rebuild path; collection recreation marks other local builds for recovery. Startup checks saved epochs even for previously clean builds. Failed projection/recovery remains visible without making canonical review depend on vector availability.
- **Semantic identity:** `semantic_identity.py` owns metadata value identity: whether two values are `exact`, `equivalent`, `different` or `unknown` under a field's `equivalence_profile`. `semantic_identity_registry.py` holds rebuildable identities projected from reviewed metadata, reviewed alias sets and (advisory) Document Intelligence clusters. `semantic_identity_store.py` persists reviewed alias sets as canonical per-build reviewer state and assembles the build and per-Record registries. Precedent matching, pre-fill voting, the adjudication cache and the Semantic Content Graph all consume the same registry. Record Review computes the relation once and passes it to feedback, evidence handling, the ledger and the audit trail. Only a `different` value becomes a rejection or correction exemplar. The registry never reads the Semantic Content Graph. Metadata equivalence never implies claim equivalence or evidentiary support.
- **Research response/claim memory:** prior Research responses, generated claims, and support bindings, owned by `research_memory.py` and `claim_memory.py`. SQLite rows are authoritative; `derridai_response_memory` (eligible responses, keyed on the question) and `derridai_validated_claims` (reviewer-validated claims with deterministic citations) are derived projections kept current through the `semantic_memory_outbox` and rebuilt when empty. A response is eligible only when graded at or above `RESEARCH_MEMORY_MIN_GRADE`. A claim is eligible for validation and the validated-claim projection only when at least one usable support binding identifies a Record; unsupported legacy rows are dropped during projection/retrieval rather than becoming trusted prose. Projection hits are re-joined to authoritative rows, and validated-claim support is checked against the run's evidence packet before it reaches the prompt. The Research answer surface exposes the same authoritative claim-validation operation used by Record Traceability, while refreshing retained-run statuses from SQLite. Claim memory remains separate from metadata exemplar retrieval; the only bridge is a read-only Record Review cross-reference (`validated_claims_citing`), which never suggests metadata.
- **Reviewer decisions:** `apply_metadata_decisions` in `corpus_review_actions.py` is the single domain operation for one or many field decisions on a record (human assertion, dispute resolution, reviewed-decision provenance, then derived adjudication memory). Routers only delegate; claim validation likewise runs through `claim_memory.apply_claim_validation`.
- **Exact adjudication cache:** deterministic/same-context assistance; it is not a substitute for evidence-bound semantic precedent.
- **Response cache:** operational RAG cache/Response Library infrastructure, not corpus truth.
- **Chroma projections:** search/vector indexes and internal semantic projections. Deleting/rebuilding them must not delete canonical review/provenance data.

Support/exemplar resolution is revision-aware. When the referenced source revision/evidence can no longer be resolved, the binding is marked stale/unresolvable rather than silently rebound to newer text.

All paths derive from `CHROMA_DATA_ROOT` (default `/data`).

Active job execution is process-local, but job snapshots/history are mirrored to SQLite. On restart, work left `queued`, `running`, or `cancelling` is marked failed/interrupted rather than automatically replayed; completed history remains inspectable. Job state is not coordinated across multiple API processes.

Corpus Builder's interactive Records are canonical rows in each build's `records.sqlite3`; JSONL is a dirty-tracked projection refreshed explicitly or at publication/export boundaries. Automatic enrichment handoffs no longer replace the corpus merely to validate it. Initial family checkpoints, initial/retry/rerun completions, and requeue-marker clearing reconcile current rows in a SQLite writer transaction and persist only changed payloads and queue contributions.

Initial family checkpoints and completions validate Record identity, revision, text, extraction text, and source bindings against their worker context inside that transaction. Retired identities are not restored; mismatches retain the current Record and log a bounded identity-only diagnostic rather than install stale assertions, stage state, counters, or a first-settled milestone. Existing requeue requests trigger a fresh pass against current state. Family callbacks merge only their own status/ledger entries, preserving siblings and human authority. Unchanged checkpoints write no Record or queue rows and schedule no exemplar projection. Selected handoffs decode only the affected Record in steady state; source-order initialization and final handoff reads remain corpus-wide. Completion notifications follow durable Record commit. Build/task summaries still have the separate post-commit durability boundary described below.

Initial enrichment queue setup also uses optimistic reconciliation: it snapshots current canonical topology, prepares operational state and initial counters outside review/writer locks, then commits changed rows together rather than using per-Record preparation writes. The same-connection data-version and schema checks reject intervening changes and retry against current state, with a visible setup conflict after three attempts. The coordinated commit guard checks cancellation and retains current settle requests and the original metadata-start timestamp during the separate counter handoff. Scholarly state and family checkpoints remain intact; unchanged rows are not written. Optional preparation stages retain conditional three-way merges. Snapshot capture, batch commit, and projection repair still require locks; this does not imply an earlier preparation unlock or a measured save-tail bound.

Full automatic validation captures all current rows in a short transaction, then decodes, validates, and prepares changes outside the manager, repository, and writer locks. Its commit transaction compares `PRAGMA data_version` on the same open connection and checks the exact metadata schema and captured build snapshot; intervening commits, schema changes, or build-only operation/review changes force a fresh snapshot and recomputation. Three conflicting attempts fail visibly. This protects against ordinary edits, direct canonical SQL writes, topology replacement, and projection repair without relying on queue counters surviving repair.

The manager coordination lock is acquired before the repository lock during capture and commit, not during validation computation. Record commit and the subsequent build-summary save remain coordinated against same-manager review mutations; the summary is still a separate durability boundary, not an atomic SQLite/JSON commit. Committed Record changes remain visible and notified even if summary storage fails. Initial/final, retry, and rerun coordinators reread current build state when closing the operation rather than saving a stale returned summary. Initial finalization reuses current retained validation instead of repeating validation against its worker's old BuildScope; retry completion reads only its selected extant identities. Cancellation requested during validation is retained and checked by the closing coordinator.

REST and frontend lifecycle gating keep review available in `finalizing_review`, without unlocking source/topology/initial annotation preparation or weakening publication gates. Validation still scans the corpus; snapshot capture/commit, cold projection repair, final operation-summary reads, and review commands themselves can still consume lock time. No browser or save-tail latency budget follows from releasing validation locks alone. Initial topology construction and actual structural replacement retain full-store saves.

`corpus_queue_projection.py` maintains versioned queue membership, search variants, facet/count contributions, and build-summary metrics in the same transaction as canonical writes. SQLite dirty-row triggers detect writes by other repository instances; reads repair dirty rows before selecting a coherent page. Initial import, schema/contract changes, missing projection tables, and explicit repair rebuild from canonical Records. Steady-state pages decode only selected payloads, and targeted edits read incremental aggregate totals and bounded issue summaries instead of scanning the corpus.

Clean selected-Record, queue, facet, and aggregate reads use a deferred SQLite snapshot rather than reserving a writer. Projection contract/schema identity, documentary-context contract, and the dirty journal are checked inside that snapshot before payloads and queue versions are read together. Dirty or incompatible state rolls back the read, repairs under repository coordination and a writer transaction, then retries; repeated repair churn fails visibly after three attempts. Storage initialization is cached by database file identity and SQLite schema version (bounded to 64 builds per repository), so warm reads perform no DDL. Atomically replaced build summaries supply the pinned schema snapshot without acquiring repository coordination on the clean path. Initialization, repair, writes, manager-level commands, and separate build-summary durability remain distinct boundaries.

Kept metadata precedent caches version 3 retain originating Record identity alongside exemplar identity. Reverification loads only referenced Records and their source units through the existing editorial-memory derivation and exact exemplar checks; target evidence remapping reads only the target's own units. Version 2 caches remain supported through their legacy corpus-resolution path because they lack Record identity. Current review authority, exact revision/evidence identity, blind opinions, reset policy, and assigned candidate-remapping pipelines still govern the result. Batch `field-precedents` reads perform no target ranking or embedding lookup: nonempty fields declare `candidates_pending`, and a visible field disclosure or explicit Evidence suggestion requests its single-field remap through the assigned pipeline. Field disclosures abort obsolete client transports on closing/hiding, context change, or disposal, and retain version checks even if a transport ignores abort. This does not cancel already-dispatched server/provider computation.

The review frontend shares matching pending neighbour and foreground Record reads by exact build/reviewer epoch, Record invalidation generation, revision and operational state version. One independent foreground transport survives repeated matching selections while selection tickets determine the only current consumer; incompatible selections and disposal abort it. Bounded neighbour admission remains best-effort, but its current foreground consumer sees failures. Visibility gates source/assistance reads and advanced JSON formatting without unmounting dirty metadata editors; recovery drafts remain independent of clean disclosure formatting.

Ordinary targeted review writes return the normalized committed payload with `queue_state_version` captured from the same SQLite writer transaction. This version describes that payload, even if notification callbacks cause a later write before the response returns. Metadata-decision reads capture payload/version together when no further write is needed. The field is transport-only: canonical encoders and publication exclude it. The frontend still reconciles membership, counts, and current versions through the queue; it reuses a saved payload only when the queue's revision and operational version both match. Optimistic edits never inherit a certified cache version. Missing versions, later enrichment, topology changes, and existing reviewer/build invalidation retain the authoritative read path.

Queue search and facets use the existing reviewer-presentation rules, including sparse first-reviewer overrides for pending blind opinions. Search remains literal casefolded Unicode JSON substring matching, not token search. Operational state versions/data generations are independent of scholarly Record revisions. Live cursors anchor source order and authenticated build/filter/reviewer context; topology changes and administrator `POST /api/pdf/corpus-builds/{build_id}/review-queue/rebuild` invalidate them. The repair response carries counts/generations only. These projections are not publication content or a replacement for canonical scholarly state.

## Document Intelligence

Corpus Builder runs provider-neutral whole-document linguistic analysis after deterministic reviewed-text cleanup and before record-level metadata enrichment. The default implementation can use local spaCy or the optional isolated BookNLP worker. Entity/coreference/quotation output is hash-bound to the analyzed text, projected onto Records as advisory context, and excluded from canonical publication JSONL.

`corpus_document_context.py` maintains a derived per-build epoch over Record text, documentary identity/locators, extraction text, and source order. Its per-Record hashes update before the shared canonical dirty journal is acknowledged, in the Record/queue writer transaction. Unrelated metadata and revision-only changes preserve the epoch. Full snapshot equivalence preserves it too; initialization/repair reconstructs the hashes and creates a new epoch. Version 2 Document Intelligence checkpoints and local projections bind that epoch and an analysis ID. Scope mismatches and mid-analysis changes remain stale; metadata routing performs a bounded epoch lookup rather than loading the corpus. Failed reanalysis replaces the current checkpoint with an unavailable result, so prior successful annotations cannot appear current. This is derived freshness state, not scholarly revision or review authority.

The derived **Semantic Content Graph** is separate from the cELF **Research Object Graph**. The former models characters/people/concepts/works/topics and content relationships for navigation and analysis; the latter models scholarly object/provenance relationships. Observational content edges (for example co-occurrence) are explicitly weaker than evidence-aware semantic edges projected from current metadata assertions. See [DOCUMENT_INTELLIGENCE.md](DOCUMENT_INTELLIGENCE.md).

## Pipeline semantics

Three separate, server-owned dimensions describe a pipeline:

- **Pipeline purpose** (`purposes.py`) is the application/research workflow contract: its workflow category (Research, Evidence, Search, Metadata, Memory, Corpus processing), the feature that consumes it, its input, output and authority semantics, and its required guarantees.
- **Strategy family** (`StageFamily`) is the computational role of one stage: retrieval, reranking, diversity, selection, context packing, generation and so on.
- **Scholarly effect** (`ScholarlyEffect`) says what, if anything, a stage establishes about evidence, support or provenance. Retrieval, fusion, reranking, diversity and selection are `advisory`: relevance never establishes support. Only `eligibility_gate` and `provenance_gate` stages validate anything, and that validation is computational, not reviewer or scholarly authority.

One strategy can serve several purposes (semantic retrieval, cross-encoder reranking and MMR each appear in more than one workflow) without becoming, say, an "evidence strategy". `workflows.py` maps each purpose to exactly one runtime adapter; compiling a graph with it is the runtime-support check, and its strategy allowlist is the source of the per-purpose `strategy_fit` served in the catalog. Structural validity (`PipelineService.validate`) and runtime executability stay separate, so structurally valid graphs outside an adapter's subset can be saved as inspect-only versions. The catalog (`GET /api/system/pipelines`) serves purposes, closed vocabularies with locale keys, strategies (with `scholarly_effect`, `phase` and `effect_note`), definitions and assignments; the frontend keeps no purpose, category or compatibility table of its own.

## Search and Research

Search can operate over browser-loaded records or server-backed corpus/vector collections. Research composes dense/lexical/MMR retrieval, deduplication and optional reranking, or can skip retrieval and synthesize from researcher-selected evidence. Evidence packets carry source identity and citation metadata into generation. Deterministic code owns stable IDs/citation resolution wherever the stored data can answer exactly.

System Data exposes administrative inspection of application/system datasets, including metadata exemplars/memory and restricted system-Chroma querying, without presenting internal vector collections as scholarly corpora.

## Frontend

`web/src/` is Vue 3 + TypeScript with Pinia and Vue Router:

- `views/` owns page composition;
- `components/` owns reusable UI/Storybook surfaces;
- `api/` owns typed transport contracts;
- `domain/` owns pure rules/formatting;
- `composables/` and `stores/` own reusable stateful behavior;
- `runtime/` is a remaining compatibility/orchestration boundary, not the preferred home for new feature logic;
- `api/graphql/` holds the typed GraphQL client and checked-in operation documents; `realtime/` holds the single WebSocket connection manager and `followResource()`;
- semantic tokens in `styles/tokens.css` and accessible primitives are the styling/interaction contract.

## Known constraints

- The application still assumes one API process for in-flight job execution and mutable embedded-storage coordination.
- The realtime broker and its replay ring are in-memory in that one process; a restart forgets events and clients resynchronize from REST.
- `chroma_store.py`, `corpus_builder.py`, and some frontend compatibility/style surfaces remain large; refactor them only along verified domain seams with regression coverage.
- Historical versioned design documents describe the release that created them, not the current architecture.

## Research thread navigation checkpoint

`research_thread_store.py` persists owner-scoped thread and turn identity in system SQLite; response-cache artifacts and process-local jobs remain separate. The frontend `ResearchThreadBrowser` reads bounded summaries and ordered turn shells through `researchThreadsApi` and `useDataQuery("research_threads")`. The existing generic data bridge invalidates these reads on thread events; no thread-specific polling loop is added. `ResearchView` owns URL selection and opens the authorized job through its existing result/evidence path. A missing job leaves its turn shell visible. Contextual follow-up submission and response-cache migration are not implemented by this navigation checkpoint.
