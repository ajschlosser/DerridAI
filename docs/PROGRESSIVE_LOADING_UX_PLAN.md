# Progressive loading UX plan

Status: implementation in progress; first Works/Record pilot checkpoint below. Source audit: 2026-10-02, `origin/master` at `ab2b097a` (application 0.81.0).

## Outcome

Navigating to a page should reveal its title, layout, and useful controls immediately after its route module is available. Data should fill the relevant regions independently. Refreshing a populated page should preserve its content, scroll, selection, and drafts, with a small status beside the region being updated. A slow secondary request should not hold the entire workspace hostage.

This document is based on inspection of the current route inventory, views, shared loading/query infrastructure, and representative nested components. It is not a browser timing or visual audit; the validation pass below is required before implementation is considered complete. No application behavior changes are included in this documentation change.

## Interaction contract

| State                          | What the user sees                                                                      | What remains usable                                               |
| ------------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| First read, no authorized data | Stable page frame and region-shaped placeholders; concise loading label                 | Navigation and controls whose dependencies are ready              |
| Same-resource refresh          | Existing data plus a small Updating status; optional last-success timestamp             | Reading, navigation, and independent actions                      |
| Successful empty read          | Specific empty state and appropriate next action                                        | Filters and creation/import controls allowed by permissions       |
| Initial read failed            | Local error with Retry, occupying the intended region                                   | Other successful regions and navigation                           |
| Refresh failed                 | Retained same-resource data, clearly marked out of date, plus retry                     | Safe reading; mutations requiring freshness await revalidation    |
| Resource/filter changed        | Placeholder for the new identity, or old results explicitly labeled as previous results | Navigation and editing the next query; no stale selection actions |
| Mutation or long job           | Busy state on the affected action/region; actual job stages when available              | Unrelated controls; cancellation where supported                  |

Use separate data availability and fetch status instead of one page-wide boolean. An empty array is not proof that loading succeeded. Request cancellation is not an error requiring an alert. Percentages must come from real progress, not timers.

Keep structural placeholders immediate; delay animated indicators approximately 150–200 ms to avoid flashes. This is an initial design target to test, not a measured optimum. Never delay real content to satisfy a minimum spinner duration. After a prolonged wait, add useful status and retry/cancel where safe without assuming the request failed.

Use compact table-row, card, form, graph, and source-preview skeleton shapes that match expected geometry. Avoid fake scholarly text, page numbers, evidence markers, citations, confidence values, or counts. Load visible/selected details first; defer collapsed heavy panels. Do not add automatic remote-model calls or load full restricted source text for prefetching.

## Implementation approach

1. Extend the existing UI primitives with compact inline status and geometry variants. Introduce a small region wrapper only if pilots demonstrate repeated conditional markup; it should receive state, not fetch data. Avoid page-wide Suspense for unrelated requests.
2. Derive initial-pending versus refreshing from `useDataQuery` where already used. Preserve the existing realtime invalidation/fallback-polling contract. Split aggregate reads only when resources are independently useful; update resource keys and invalidation mappings together. Concurrent requests alone are insufficient if one aggregate promise still gates presentation.
3. For runtime-backed workspaces, put new presentation and request coordination in typed Vue composables/services. Reuse existing adapters while extracting only the minimum boundary needed. Do not expand legacy DOM renderers.
4. Key reads by authorized scope and actual identity: account/role where necessary, corpus/publication, record/revision, collection, filters, sort, pagination, and locale where the returned content depends on locale. Cancel superseded requests or ignore their results using existing latest-request machinery. Dedupe matching reads. Bound retained data and clear sensitive caches on logout/permission changes.
5. Preserve same-resource data through refresh failures, but keep freshness/error metadata visible. Apply results atomically where evidence, text, and revision must agree. Never patch a newly selected record with an old response. Background updates must not overwrite drafts or human review decisions; reuse the existing newer-data notification pattern.
6. Preserve view preferences and selected IDs deliberately. Use the shared cache for server data; do not put the whole app under KeepAlive just to avoid loaders. Restore scroll/focus on back navigation where appropriate without retaining obsolete permissions or live subscriptions.
7. Add route-module navigation feedback separately from data feedback. If chunk timing proves material, prefetch authorized route modules on user intent with bounded work. Data prefetch and API envelope changes require evidence from the pilot; they are not prerequisites for localized loading.

## Validation and success criteria

Before implementation, capture baseline and after-change results for cold navigation, warm revisit, same-route refresh, and selection change. Measure navigation-to-frame, navigation-to-first-useful-content, each region's readiness, content displacement, and request counts separately. Use deterministic fixture delays (fast, 1 second, and 5 seconds) and individual endpoint failures; do not describe synthetic results as production latency.

Acceptance checks:

- Once a route module is ready, show its static frame without waiting for data. In a cached same-resource refresh, do not unmount visible content or reset focus, scroll, filters, expanded panels, or drafts.
- Under a five-second secondary-panel delay, already available primary content remains readable and usable. One failed panel does not remove successful siblings.
- Cold reads never flash a false empty state. New selections never show mismatched record text, source pages, evidence, or revisions. Rapid A → B navigation with A resolving last still displays B.
- Refresh failures show stale/unavailable state explicitly. Authentication/authorization failures clear inaccessible data; initial authentication may remain a legitimate global gate.
- A slow read disables only dependent actions. Genuine atomic edits, authorization, and operations requiring a validated snapshot can retain narrowly scoped blocking states with a stated reason.
- Add Vitest coverage for state transitions and stale responses; Playwright delayed-route tests for DOM preservation, partial failure, back navigation, and job/read separation. Use Storybook for all skeleton geometries and error states.
- Verify keyboard navigation and focus, local `aria-busy`, one polite status announcement per meaningful region transition, decorative skeletons hidden from assistive technology, reduced motion, light/dark themes, narrow widths, long French labels, and browser zoom. Avoid announcing every polling or realtime update.
- Run targeted frontend tests, typecheck, localization parity, Storybook/accessibility checks, and production build for implementation changes. Check that splitting queries does not multiply identical requests or introduce new polling.

Document validation for this plan: source review only; no running-app observations or performance claims. Validate Markdown formatting, repository diff hygiene, and referenced source paths before committing. Application tests are unnecessary for this documentation-only change.
