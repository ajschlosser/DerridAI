# Progressive loading UX plan

Status: workspace-by-workspace implementation and source audit complete on 2026-10-06. Final quality-gate validation is tracked on the completion branch; earlier checkpoint/resume notes below are historical. Source audit began 2026-10-02 at `origin/master` `ab2b097a`.

## Outcome

Navigating to a page should reveal its title, layout, and useful controls immediately after its route module is available. Data should fill the relevant regions independently. Refreshing a populated page should preserve its content, scroll, selection, and drafts, with a small status beside the region being updated. A slow secondary request should not hold the entire workspace hostage.

### Route-commit checkpoint — 2026-10-06

Top-level route-module loading no longer owns navigation completion. Each application route now commits through a synchronous progressive entry component; breadcrumbs, active navigation state, URL/history and the destination loading frame can update before the destination JavaScript chunk resolves. The code-split view module loads inside that committed route. The wrapper starts the chunk read immediately but deliberately gives the destination skeleton a browser paint before mounting the real page, so even a cached module with expensive synchronous setup cannot make the previous page appear to linger. Ordinary module-load failures keep the destination committed and expose explicit recovery. Retry reloads that destination because browsers may cache a failed ES-module fetch for the lifetime of the document; the existing stale-deployment recovery remains responsible for replaced hashed chunks.

Corpus Builder/Source Explorer and the System Data sibling routes deliberately share their progressive entry object so this change does not turn sibling navigation into a remount boundary. A focused router regression keeps a destination chunk unresolved and requires `router.currentRoute` plus the destination skeleton to update before that promise settles.

This fixes route-module blocking. The completed inventory below is the authority for page-local data boundaries and documented atomic dependencies.

### Corpus Builder route-critical hydration checkpoint — 2026-10-06

Corpus Builder now restores a route-addressed build and its requested review topology independently of Setup-supporting provider, corpus-profile, and source-catalog reads. Those supporting reads still begin at mount, but they no longer sit in the prerequisite `Promise.all` ahead of `refreshBuild()` and review hydration. A deep link to Build, Review, or Publish can therefore establish its authoritative build context while slower Setup data continues to hydrate.

The change does not weaken build authority or review provenance: the build list still resolves the selected build, `refreshBuild()` remains the authoritative build snapshot, and review hydration still follows that selected build. A focused frontend regression holds the asset-list read unresolved and requires the requested review build and queue to hydrate before that support read completes. The later preview-identity re-audit below closes the remaining source-preview identity boundary.

This document combines source inspection with the focused unit/browser evidence recorded in the checkpoints below. Synthetic delays and request counts validate behavior but are not production latency measurements.

### Operations and Compare workspace checkpoint — 2026-10-06

Operations no longer waits for an external jobs refresh before mounting its page content. The Vue Operations panel owns the initial refresh: an unresolved first read shows region-shaped loading feedback rather than a confirmed-empty message, a refresh over known operations retains those rows, and transport failure stays local with Retry. Because the same panel is embedded on Home, the dashboard now mounts that region before its unrelated dashboard refresh completes.

Compare now mounts both record panes, source tabs, editors, and actions before the record library finishes hydrating. Library loading and failure are local to the library source region, request completions are ignored after unmount, and the page withholds both the "library empty" and "two records are needed" claims while a required library read is still pending. Scratch/editor comparison remains usable independently of that read.

Providers was re-audited against its actual data contract. Profile/status initialization is synchronous local application state, not an asynchronous read, so the one-frame loading card was misleading rather than protective. The view now reads that state during component setup and renders the actual provider workspace on the first frame; remote test/warm/save operations retain their existing per-action busy/error states.

System Data's Advanced, Saved Responses, and Metadata Examples regions now distinguish first reads, same-identity refreshes, and changed result identities. Advanced retains a successful internal-vector collection snapshot and read-only console while refreshing, and an ordinary refresh failure no longer becomes a false empty collection. Saved Responses and Metadata Examples retain same-query/filter rows during refresh and stale failure, but suppress prior rows when the search/filter/page identity changes. Metadata Examples also withholds its count until the requested identity succeeds and closes a detail panel when that identity changes.

Focused regressions cover unresolved initial Operations refresh, retained Operations content after refresh failure, Compare controls during a deliberately held library read, library failure without replacing the workspace, first-frame Providers rendering, retained System Data vector collections, retained Saved Responses/Metadata Examples on same-identity refresh failure, and suppression of previous results under a newly requested identity.

### System Data database-browser checkpoint — 2026-10-06

The Databases workspace no longer makes its directory wait for the selected table-row read. A successful database/table catalog becomes usable immediately and row hydration proceeds as an independent region. Catalog refresh retains the last successful directory and reports stale failure locally instead of replacing known structure with a page-wide error.

Table rows now carry an explicit database/table/page identity. Refreshing the same identity retains the visible rows and reports progress or stale failure in place. Selecting a different table or page withholds the previous rows until that new identity succeeds, and late responses from superseded requests are ignored. Row details are likewise bound to the currently displayed table identity.

Focused regressions hold the first table read unresolved while requiring the database directory to be usable, retain rows through a same-table refresh failure, and require old rows to disappear while a different table identity is pending.

### Pipeline Studio region-hydration checkpoint — 2026-10-06

Pipeline Studio now treats its catalog, execution history, and operational-health metrics as independent server-state regions. The page header and section tabs remain usable while execution rows or health metrics are unresolved. Execution rows are bound to the exact filter/page identity that produced them: same-identity refreshes retain the last successful page, while a new filter or page withholds the prior rows until the requested identity succeeds. This prevents a previous result set from being presented under a newly requested query.

Operational-health loading is likewise local to the Health panel, so Compare and Benchmarks navigation is available without waiting for metrics. Catalog refresh remains the only workspace-wide dependency because definitions, strategy vocabulary, purposes, and assignments are the structural contract for every Pipeline Studio section. A successful catalog remains mounted during background invalidation.

Focused regressions hold the initial execution-page and metrics requests unresolved and require the destination-owned controls and section navigation to render before those reads complete.

### Search workspace checkpoint — 2026-10-06

The unresolved frame keeps scope/view actions and the query input visible but disabled, withholds collection/evidence counts rather than synthesizing zeros, and confines skeletons to the explorer regions. A failed first read keeps that same frame and exposes Retry locally instead of replacing the page or claiming that no records match.

The existing Search retained-refresh and result-identity protections remain in force. A same-context refresh keeps successful content mounted; access withdrawal clears retained data; superseded reads cannot overwrite newer navigation; and a newly submitted corpus-database query replaces previous rows with a searching state until the requested result identity succeeds. Its page header and composer mount before the authoritative workspace snapshot, the Run action remains disabled until its required inputs are ready, and a prompt typed during the first read survives snapshot application. ### Sources capture-discovery checkpoint — 2026-10-06

Sources already had separate table and inspector ownership, including in-place table reloads after capture changes. The remaining false-empty boundary was the independent capture catalog: its initial empty array rendered “no captures” before the authoritative capture-list request had completed, and a failed request replaced that region with an error without an explicit retry path.

Capture discovery now has explicit unresolved, available, and unavailable states. An unresolved first read uses capture-shaped skeletons and withholds the empty-capture claim. Failure remains local to the capture region with Retry while the source table stays mounted and usable. A successful empty response is the only state that renders the empty-capture message. Existing capture completion continues to refresh the table in place rather than remounting it.

Focused regressions hold the first capture read unresolved while requiring the source table to remain mounted, then verify that an empty message appears only after a successful response. A failed first capture read likewise keeps the table mounted, withholds the empty claim, and recovers through the local Retry action.

The table and inspector now complete the same identity contract. A same-query table refresh retains useful rows, while a different filter/sort/page/queued-source identity clears the prior result page and hidden bulk selection before the new read resolves. The page also drops an inspector selection that no longer belongs to the displayed result identity. Inspector detail and extracted-text preview reads are generation-guarded: changing source identity clears the previous facts immediately and late responses from the old source cannot overwrite the new one.

### Metadata Schemas catalog/detail checkpoint — 2026-10-06

The Metadata Schemas route already mounted its page frame independently of provider-profile state, but the editor itself treated catalog discovery and schema detail reads as implicit operations. Initial catalog failure could escape the component, and rapid schema selection could leave the previous draft visible while a new identity was loading or allow a late response to win.

The editor now separates catalog readiness from schema-detail readiness. The first catalog read has a library-local skeleton/error/Retry state; a successful catalog stays mounted through refresh. Selecting a different schema clears the previous draft immediately and shows an editor-local placeholder until the requested schema arrives. Detail reads are generation-guarded, so superseded selections cannot overwrite the current schema. Save/import/delete/preview operations continue to use the existing mutation busy state and dirty-draft protection.

Focused regressions hold the first catalog read unresolved and verify that neither a false empty library nor an editor draft is presented. A rapid Notes → Fiction selection then resolves the older Notes request last and verifies that Fiction remains authoritative.

### Home region-readiness checkpoint — 2026-10-06

Home previously mounted immediately but initialized its remote-backed arrays and counts to empty/zero while one sequential refresh awaited researcher store/work data, annotations, and the record preview. That made an unresolved first read observationally identical to a genuinely empty corpus or activity stream and allowed the preview read to delay unrelated dashboard derivation.

The dashboard now has separate core-corpus, activity, and record-preview readiness. Corpus/Works counts and charts become authoritative after the store/work read; activity refreshes annotations independently; preview hydration is independent of both. First reads withhold zero/empty claims and show local loading geometry. A researcher store read that fails before any authorized data is known leaves the corpus region unavailable rather than asserting an empty corpus. Same-context failures retain known data with stale feedback and Retry. The Operations region remains independently owned by its existing panel host.

This is a presentation/readiness split only: search behavior, corpus/store selection policy, annotation semantics, job lifecycle, and dashboard navigation are unchanged.

### Corpus Builder / Source Explorer preview-identity re-audit — 2026-10-06

The current workspace shell already satisfies the major navigation/loading boundaries established earlier in the navigation plan: Builder and Source Explorer are retained siblings under `KeepAlive`; each route keeps its own query-state whitelist and remembers its own addressable context; the Builder's deep-link restoration prioritizes build/review state ahead of Setup-supporting reads; and evidence/PDF rendering owns cancellation locally.

One remaining identity mismatch existed in `PdfEvidenceViewer.vue`. Its canvas could retain pixels from page A while the route/component prop had already changed to page B, causing the canvas label, caption, and source-box overlay to describe B before B had actually rendered. The viewer now commits a separate `displayedPage` only after a render completes. A document change clears the old canvas identity; a page change keeps old pixels associated with the old page until canvas replacement begins, then exposes loading state until the new render commits. Source-box overlays are keyed to the displayed page rather than the requested page.

This preserves the scholarly source-binding invariant: visible source imagery and accessibility metadata cannot claim a page identity that has not been rendered. No PDF extraction, layout, evidence, review, or publication semantics changed.

## Interaction contract

| State                          | What the user sees                                                                      | What remains usable                                               |
| ------------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| First read, no authorized data | Stable page frame and region-shaped placeholders; concise loading label                 | Navigation and controls whose dependencies are ready              |
| Same-resource refresh          | Existing data plus a small Updating status; optional last-success timestamp             | Reading, navigation, and independent actions                      |
| Successful empty read          | Specific empty state and appropriate next action                                        | Filters and creation/import controls allowed by permissions       |
| Initial read failed            | Local error with Retry, occupying the intended region                                   | Other successful regions and navigation                           |
| Refresh failed                 | Retained same-resource data, clearly marked out of date, plus retry                     | Safe reading; mutations requiring freshness await revalidation    |
| Resource/filter changed        | Placeholder for the new identity, or old results explicitly labeled as previous results | Navigation and editing the next query; no stale selection actions |
| Mutation or long job           | Busy state on the affected action/region; actual job stages when available              | Unrelated controls; cancellation where supported                  |

Use separate data availability and fetch status instead of one page-wide boolean. An empty array is not proof that loading succeeded. Request cancellation is not an error requiring an alert. Percentages must come from real progress, not timers.

Keep structural placeholders immediate; delay animated indicators approximately 150–200 ms to avoid flashes. This is an initial design target to test, not a measured optimum. Never delay real content to satisfy a minimum spinner duration. After a prolonged wait, add useful status and retry/cancel where safe without assuming the request failed.

Use compact table-row, card, form, graph, and source-preview skeleton shapes that match expected geometry. Avoid fake scholarly text, page numbers, evidence markers, citations, confidence values, or counts. Load visible/selected details first; defer collapsed heavy panels. Do not add automatic remote-model calls or load full restricted source text for prefetching.

## Implementation approach

1. Extend the existing UI primitives with compact inline status and geometry variants. Introduce a small region wrapper only if pilots demonstrate repeated conditional markup; it should receive state, not fetch data. Avoid page-wide Suspense for unrelated requests.
2. Derive initial-pending versus refreshing from `useDataQuery` where already used. Preserve the existing realtime invalidation/fallback-polling contract. Split aggregate reads only when resources are independently useful; update resource keys and invalidation mappings together. Concurrent requests alone are insufficient if one aggregate promise still gates presentation.
3. For runtime-backed workspaces, put new presentation and request coordination in typed Vue composables/services. Reuse existing adapters while extracting only the minimum boundary needed. Do not expand legacy DOM renderers.
4. Key reads by authorized scope and actual identity: account/role where necessary, corpus/publication, record/revision, collection, filters, sort, pagination, and locale where the returned content depends on locale. Cancel superseded requests or ignore their results using existing latest-request machinery. Dedupe matching reads. Bound retained data and clear sensitive caches on logout/permission changes.
5. Preserve same-resource data through refresh failures, but keep freshness/error metadata visible. Apply results atomically where evidence, text, and revision must agree. Never patch a newly selected record with an old response. Background updates must not overwrite drafts or human review decisions; reuse the existing newer-data notification pattern.
6. Preserve view preferences and selected IDs deliberately. Use the shared cache for server data; do not put the whole app under KeepAlive just to avoid loaders. Restore scroll/focus on back navigation where appropriate without retaining obsolete permissions or live subscriptions.
7. Add route-module navigation feedback separately from data feedback. If chunk timing proves material, prefetch authorized route modules on user intent with bounded work. Data prefetch and API envelope changes require evidence from the pilot; they are not prerequisites for localized loading.

## Validation and success criteria

Before implementation, capture baseline and after-change results for cold navigation, warm revisit, same-route refresh, and selection change. Measure navigation-to-frame, navigation-to-first-useful-content, each region's readiness, content displacement, and request counts separately. Use deterministic fixture delays (fast, 1 second, and 5 seconds) and individual endpoint failures; do not describe synthetic results as production latency.

Acceptance checks:

- Once a route module is ready, show its static frame without waiting for data. In a cached same-resource refresh, do not unmount visible content or reset focus, scroll, filters, expanded panels, or drafts.
- Under a five-second secondary-panel delay, already available primary content remains readable and usable. One failed panel does not remove successful siblings.
- Cold reads never flash a false empty state. New selections never show mismatched record text, source pages, evidence, or revisions. Rapid A → B navigation with A resolving last still displays B.
- Refresh failures show stale/unavailable state explicitly. Authentication/authorization failures clear inaccessible data; initial authentication may remain a legitimate global gate.
- A slow read disables only dependent actions. Genuine atomic edits, authorization, and operations requiring a validated snapshot can retain narrowly scoped blocking states with a stated reason.
- Add Vitest coverage for state transitions and stale responses; Playwright delayed-route tests for DOM preservation, partial failure, back navigation, and job/read separation. Use Storybook for all skeleton geometries and error states.
- Verify keyboard navigation and focus, local `aria-busy`, one polite status announcement per meaningful region transition, decorative skeletons hidden from assistive technology, reduced motion, light/dark themes, narrow widths, long French labels, and browser zoom. Avoid announcing every polling or realtime update.
- Run targeted frontend tests, typecheck, localization parity, Storybook/accessibility checks, and production build for implementation changes. Check that splitting queries does not multiply identical requests or introduce new polling.

Document validation for this plan: source review only; no running-app observations or performance claims. Validate Markdown formatting, repository diff hygiene, and referenced source paths before committing. Application tests are unnecessary for this documentation-only change.
