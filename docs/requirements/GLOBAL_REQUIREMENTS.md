# DerridAI Global Product Requirements

**Document type:** Product Requirements / Traceability Matrix  
**Scope:** Product-wide  
**Baseline:** `master` at creation of this requirements baseline  
**Related specification:** [cELF 1.0](../../SPECIFICATION.md)

## Purpose

This document defines product-wide requirements that apply across DerridAI. Detailed area requirements inherit these requirements and should trace back to them.

The global requirements intentionally focus on durable product invariants rather than page-specific behavior.

## Verification legend

| Coverage | Meaning |
| --- | --- |
| **Direct** | One or more automated tests directly exercise the requirement or a principal invariant defined by it. |
| **Partial** | Automated tests cover important parts of the requirement, but the requirement is broader than any single test. |
| **Architectural** | No single automated test establishes the full requirement; conformance requires design/code review plus lower-level tests. |
| **Gap** | The requirement lacks adequate automated verification. |

## Product-level definition of done

A feature or product requirement is complete only when all applicable conditions are met:

1. Functional acceptance criteria are implemented.
2. Applicable cELF and `PRD-G-*` invariants remain satisfied.
3. Provenance and authority semantics have been reviewed.
4. User-visible copy is localized for supported built-in locales.
5. WCAG 2.2 AA implications have been addressed.
6. Responsive behavior has been reviewed for affected layouts.
7. Relevant state is route-addressable when safe and useful.
8. Sensitive/transient state is excluded from shareable URLs and inappropriate persistence.
9. Error, empty, loading, fallback, stale, and unavailable states are defined.
10. Applicable automated tests are added or updated.
11. Regression, type, formatting, build, contract, localization, and accessibility gates pass.
12. Reusable UI introduced by the feature has appropriate component/Storybook coverage where applicable.
13. Help/contextual guidance is updated for new routes, concepts, parameters, failure modes, or consequential actions.
14. Durable schema/API/pipeline changes define compatibility behavior.
15. The implementation does not introduce hard-coded scholarly field behavior when an existing generic schema or FieldAssertion contract can express it.

## Change control

Changes to a `PRD-G-*` requirement are product-architecture changes.

A pull request that modifies, removes, or creates an exception to a global requirement should identify the affected requirement ID, explain the rationale, identify affected product/cELF areas, update this document, update automated coverage where applicable, and document migration/compatibility behavior for durable state.
